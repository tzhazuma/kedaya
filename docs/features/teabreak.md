# 学术会议茶歇分享（`teabreak`）

> 2026-10-22 新建。模块 id `teabreak`，第 24 个契约模块（17 个业务模块之一）。

---

## 0. 一句话

同学把**校内学术会议**的时间、地点、有没有茶歇报上来，
其他人据此判断「现在这栋楼里哪间会议室正在发点心」。

---

## 1. ⚠️ 这个功能的核心不是「列表」，是「**多久没被确认了**」

一个会议茶歇通常只有 **15–30 分钟**。
所以一条茶歇信息的**半衰期极短** —— 昨天的信息等于没有。

这决定了整个设计：

| 设计 | 为什么 |
| --- | --- |
| 每条显示「还有 X 分钟结束」 | 决定「来得及吗」 |
| 每条显示「X 分钟前确认」 | 决定「大概率还有吗」 |
| **20 分钟新鲜度阈值** | 超过就降级为 `stale` |
| 「我去看了，还有」按钮 | 这是唯一靠得住的数据来源 |

### 新鲜度四态

| 状态 | 判据 | 值不值得去 |
| --- | --- | --- |
| `fresh` | 时间窗内 **且** 20 分钟内有人确认 | ✅ 大概率还有 |
| `stale` | 时间窗内，但 >20 分钟没确认 / 从没确认 | ✅ **仍然值得去**，但文案要说「可能还有」 |
| `notStarted` | 还没到开始时间 | ❌ |
| `over` | 已过结束时间 | ❌ **即使刚刚有人确认过** |

> ⚠️ 最后一条是刻意的：`worthGoing` 看的是**时间窗**，不是新鲜度。
> 有人 5 分钟前说「还有」，但结束时间已过 —— 那就是收摊了。
> 这条有专门的测试守着。

---

## 2. ⚠️ 关于「蹭会」：不谴责，但必须说清楚

真实情况是分裂的：有些会议茶歇对整层楼开放，有些只对注册参会者。
想去的同学自己会权衡风险 —— **被工作人员请出去比少吃一块蛋糕难受得多**。

所以有三种 `access`，每种都有**风险提示**：

| access | 标签 | 提示 |
| --- | --- | --- |
| `open` | 对外开放（不需注册） | 通常会有人指引，可以直接过去。 |
| `registered` | 仅限注册参会者 | 需要会议注册证或胸牌，可能被工作人员询问。 |
| `unknown` | 不确定 | 发布者也不确定。建议在门口观察一下，或找认识的参会者带进去。 |

**为什么不说教**：写「请勿蹭会」既没用也让人反感。只说事实 ——
去了可能被问「你是哪位」，这个信息本身足够用户做决定。

**为什么不加「实时人数」**：那会把这个功能变成「监控会议室」的工具，
而且需要摄像头/传感器，与这个模块的轻量定位不符。

---

## 3. 排序：先冲哪个

```
1. worthGoing 为真的排前面
2. 同样值得去：fresh 排在 stale 前面
3. 同样新鲜度：茶歇**结束得早**的排前面   ← 快没了，先冲这个
4. 最后按开始时间
```

第 3 条是这个功能最实际的一条：两个茶歇都还有，一个 20 分钟后结束、
一个 2 小时后结束 —— 显然先去前者。

## 4. 校验规则

| 规则 | 理由 |
| --- | --- |
| 会议名 3–80 字 | 太短认不出是哪个会 |
| 地点 2–60 字 | 要写清楼和房间号 |
| 会议结束 > 开始 | — |
| 茶歇窗口 **10 分钟 – 3 小时** | 再短不是茶歇；再长可能是午餐 |
| **茶歇必须在会议时间窗内**（允许贴边） | 否则是填错了 |
| 已结束的会不能发 | 发出来也没人去 |

## 6. 演示数据为什么不会过期

小程序页里的 `demoTeabreaks(now)` **全部相对 `now` 生成**：

```ts
const at = (offsetMin: number): string =>
  new Date(now.getTime() + offsetMin * MINUTE).toISOString();
```

四条数据分别是 `-30~+20 分钟`（fresh）、`-40~+15`（stale）、
`+150~+180`（notStarted）、`-25~-24.5 小时`（over）。
所以**无论哪天打开**，都能看到四种状态各一条。

⚠️ 这一条是上一轮 CI 失败的教训：
`apps/web/src/data/mock/fixtures/buddy.ts` 的 `localAt` 用 `setHours`（本地时区），
导致 fixture 的「确定性」是假的。**本模块的演示数据只用毫秒偏移，不碰时区。**

## 7. 已知空缺

| 项 | 状态 |
| --- | --- |
| **服务端接口** | ❌ **没有**。数据暂存本机，`delivery.ts` 的 note 已如实写明 |
| 会议自动发现 | ❌ 未做（需要抓学校会议通知，见下文） |
| 重复确认的去重 | ❌ 只做本地 |
| 跨端同步 | ❌ 无后端就没有 |

### 接后端时要做什么

1. `services/api/src/modules/teabreak/`：CRUD + 确认
2. **确认接口要做频控** —— 否则一个人点十次就能把 `stale` 刷成 `fresh`
3. 可以考虑「过期自动归档」：`teaEndsAt < now - 1h` 的记录不再返回

### 一个可能的增强（没做）

学校有会议通知页面（`www.shanghaitech.edu.cn` 的「活动」栏目）。
理论上可以抓「本周学术会议」自动生成候选，让用户只需填「有没有茶歇」。
**没做**，因为：
- 会议通知页面是 JS 渲染的（上一轮实测 `fresh` 站 HTML 里什么都没有）
- 而且「有没有茶歇」这件事**只能人肉确认**，自动抓会议时间只省了一小步
