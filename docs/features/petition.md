# 众筹诉求（`petition`）—— 把共同需求变成一封可核对的信

> 2026-10-21 新建。模块 id `petition`，第 23 个契约模块（16 个业务模块之一）。

---

## 0. 一句话

**这里的「众筹」不筹钱，筹的是「有多少人真的需要」。**
达到门槛后，由发起人把一封格式化的邮件发给对应部门。

---

## 1. 为什么不做成「筹钱」

用户最初的说法是「众筹平台，如果同学们有一定的共同需求可以向对应的学校部门进行联系」。

要把这句话变成产品，「众筹」有两种读法：

| 读法 | 产物 | 结论 |
| --- | --- | --- |
| 筹**钱**（凑钱办活动/买设备） | 需要支付、退款、分账、资金托管 | ❌ **不做** |
| 筹**诉求证据**（凑人数向学校提需求） | 附议计数 + 邮件生成 + 状态追踪 | ✅ 本模块 |

**为什么坚决不碰资金**：一旦有资金流转，性质就变成支付业务 ——
需要《支付业务许可证》、商户号、风控体系、资金存管。
一个学生项目做这个既是法律风险，也没必要 —— 同学们真实的需求
九成是「希望学校改点什么」，而不是「我们希望凑钱买个东西」。

所以代码里**没有任何金额字段**。这不是还没做，是**故意不做**。

---

## 2. 三个角色，三种可见性

| 角色 | 是否实名 | 为什么 |
| --- | --- | --- |
| **发起人** | ✅ 必须实名 | 部门需要一个能联系的人 |
| **附议者** | ❌ 匿名 | 部门只需要知道「有多少人」，不需要「是谁」 |
| **对接部门** | 公开 | 邮件收件人必须可见、可核对 |

### ⚠️ 关于附议匿名的实现细节

`PetitionEndorsement` **不存 userId**，只存：

```ts
{ endorsementId: string,   // 随机串，仅用于去重
  endorsedAt: string,
  note: string | null }    // 附议者留的话，默认不进邮件
```

这意味着：**服务端无法证明某个学号支持了某条诉求。**
即便被要求调数据，也给不出一份「谁支持了什么」的名单。

代价：理论上换设备可以重复附议。**我们接受这个代价** ——
宁可人数统计不完美，也不建立支持者档案。

## 3. 阈值：分档，且每档有理由

```ts
petitionThreshold(scope, urgent)
```

| 影响范围 | 门槛 | 理由 |
| --- | --- | --- |
| `personal` 个人不便 | 10 | 一个人提容易被当成个例；10 人能说明不是偶发 |
| `group` 部分同学 | 30 | 一个班级/社团量级，部门会认真看 |
| `campus` 全校性 | 100 | 涉及全校调整，需要足够样本 |

`urgent`（安全隐患、影响正常上课）时**门槛减半**，下限 3 ——
紧急的事不该卡在人数上。

> ⚠️ 这些数字**不是权威数据**，是让流程能启动的经验值。
> 一旦有部门给出正式口径，改 `PETITION_BASE_THRESHOLDS` 并更新测试。

## 4. ⚠️ 最重要的设计：`ready` ≠ `submitted`

状态机：

```
draft ──发布──> collecting ──到阈值──> ready
                   │                     │
                   │                     └──发起人点发送──> submitted
                   └──撤回──> withdrawn            submitted ──部门回复──> answered
                                                                answered ──> resolved | rejected
```

**为什么必须两个状态**：

- `ready` = 人数够了
- `submitted` = 邮件**真的发出去**了，且有回执（发送方、时间、主题）

混成一个会产生最坏的失败模式：**「以为反映了，但实际上没人发」**。
所以 `suggestPetitionStatus()` **永远不返回 `submitted`** ——
那需要有人真的点了发送。测试锁住了这一条。

## 5. 邮件生成

`buildPetitionEmail(petition, now)` → `{ to, subject, body }`

### 三条硬约束

1. **只用可核对的数字** —— 附议数来自 `endorsements.length`，
   不接受调用方传入的「支持人数」。
2. **不列支持者名单，也不转发附议者留言** ——
   那些话是在站内说的，未经本人同意不该原样转给部门。
   （测试里专门有一条断言「附议者留言不能出现在邮件里」。）
3. **人不够时抛 `RangeError`** —— 不允许「人不够也发」。

### 邮件长这样

```
收件人：logistics@shanghaitech.edu.cn
主题：  【学生诉求】希望二食堂增加素食窗口（30 位同学附议 · P-2026-001）

后勤服务中心 老师：

您好。我们是提交本诉求的同学代表。以下内容由可达鸭校园服务平台汇总，
附议数据可在平台核对。

【诉求】希望二食堂增加素食窗口
【类别】食堂餐饮　【影响范围】部分同学
【附议人数】30 人（门槛 30 人）
【征集时间】2026-10-01 至 2026-11-01

【详细说明】
目前二食堂素食选择很少……（诉求原文）

【发起人】
张三

【联系方式】
回复本邮件即可，我们会转达发起人。

—
诉求编号：P-2026-001
发送时间：2026-10-21T…
本邮件由可达鸭（第三方非官方平台）代学生发送，不代表学校立场。
```

## 6. 默认对接部门

| 类别 | 部门 | 邮箱 |
| --- | --- | --- |
| 食堂餐饮 | 后勤服务中心 | `logistics@…` |
| 公共设施 | 后勤服务中心 | `logistics@…` |
| 教学教务 | 教务处 | `academics@…` |
| 宿舍生活 | 学生事务处 | `student@…` |
| 校园信息化 | 信息化办公室 | `it@…` |
| 其他 | 校长办公室 | `office@…` |

> ⚠️ **这些邮箱是建议值，不是官方确认的。**
> UI 必须让发起人在发送前核对 —— **发错部门比不发更糟**（部门会当成垃圾邮件）。
> 所以页面只**生成**邮件，**不替用户按发送**。

## 8. 已知空缺

| 项 | 状态 |
| --- | --- |
| **服务端接口** | ❌ **没有**。数据暂存本机，`delivery.ts` 的 note 里已如实写明 |
| 邮件实际发送 | ❌ 只生成正文，由用户在邮箱里自己发 |
| 部门回执解析 | ❌ 未做 |
| 重复附议的强去重 | ❌ 只做本地去重（换设备可重复，见 §2） |

### 接后端时要做什么

1. `services/api/src/modules/petition/`：CRUD + 附议（服务端也要做**某种**去重，
   但**不能用学号** —— 用设备指纹或 IP+时间的弱去重，宁可漏也不要建立支持者档案）
2. 邮件发送用 `services/api` 已有的邮件通道（`imapflow` 只做收，发送需 SMTP）
3. 把 `delivery.ts` 的 note 里「服务端还没有对应接口」删掉
