# 15 · 校园卡付款码：真实机制与可行路径

> 2026-10-20。回答：「搜索微信里面的上科大一卡通小程序，分析是怎么获得付款码的」。
>
> **结论先说**：付款码**不是**可以抓的一个接口，它是一套**校方与腾讯微校的合作机制**。
> 拿到老师授权之后，正确做法是**向校方要接口文档**，而不是逆向小程序。

---

## 1. 一卡通小程序里那个码是什么

用户在微信里点开「上科大一卡通」小程序，屏幕上出现一个**不断刷新的二维码**。
商户用扫码枪/收银机扫这个码完成扣款。

这个码在腾讯的体系里叫 **校园码（校园卡电子码）**。它的官方定义：

> 校园码可以理解为原校园卡二维码的升级，校园码可以实现：
> 快速解码，甚至**校内部署**，短期断外网也可用，保证服务高可用；
> 可以同时支持**一卡通支付、微信支付、身份认证**。
>
> —— [腾讯微卡 Wiki · 校园码解码](https://wiki.weixiao.qq.com/api/v1/school/campuscode.html)

关键点：

| 特性 | 含义 |
| --- | --- |
| **动态** | 码会过期刷新，不是静态卡号 |
| **加解密方法有变动** | 新版码长度 80–150 字节，前缀 `wxcc://` 或 `http://wx.url.cn/` |
| **支持校内部署** | 学校可以自建解码服务，断外网也能用 |
| **一码多用途** | 支付 / 门禁 / 签到共用同一套码 |

## 2. 官方只开放「解码」，不开放「生成」

这是最关键的一条。腾讯微校开放的接口是：

```
POST https://weixiao.qq.com/apps/school-api/campus-code
Content-Type: application/json

{
  "app_key":    "APP_KEY",
  "timestamp":  1514276659,
  "nonce":      "5K8264ILTKCH16CQ2502SI8ZNMTM67VS",
  "signature":  "A790E009D30C09BD8605810EAF9C44B0",
  "school_code":"4144010559",
  "auth_code":  "http://wx.url.cn/v001.Eee8m...kA",
  "scene":      2,
  "device_no":  "device-1213",
  "location":   "三食堂"
}
```

| 参数 | 说明 |
| --- | --- |
| `auth_code` | **扫码获得的动态码** —— 也就是从用户屏幕上扫下来的那串 |
| `scene` | 1=门禁 2=消费 3=签到 4=其它 |
| `device_no` / `location` | 哪台设备、在哪个地点 |

返回：

```json
{
  "code": 0,
  "offline": 0,
  "user": {
    "card_number": "07302590",
    "name": "陈小明",
    "identity_type": "1",
    "college": "人居环境工程学院",
    ...
  }
}
```

### ⚠️ 看懂这个方向性差别

| 能力 | 谁有 | 我们能不能做 |
| --- | --- | --- |
| **显示一个付款码**（生成） | 校方一卡通系统 / 腾讯微校的小程序 | ❌ **没有公开接口** |
| **解码一个被扫的付款码** | 商户收银端 | ✅ 有接口，但需要 `app_key` + 签名（合作方资质） |

**这个 API 是「收银台那一侧」的接口，不是「用户手机那一侧」的。**

用户手机上那个码由**一卡通核心系统**签发 —— 也就是学校的「一卡通平台」。
腾讯微校只是壳。

## 3. 参考项目 TechPie 是怎么做的（以及我们为什么不抄）

`docs/features/techpie-integration.md` §2.5 记录了实测结论：

| 证据 | 内容 |
| --- | --- |
| `ecard_api_client.dart:110` | eCard API 直连 `https://ecard.shanghaitech.edu.cn` |
| `ecard_openid_auth_port.dart:30` | `baseUrl = 'https://ecard.shanghaitech.edu.cn'` |
| `campus_card_service.dart:195-233` | 用 **OPENID** 绑定（`EcardOpenIdChannel.wechat`），**不走 CASTGC** |
| `ecard_bind_hijack.dart:52` | `static const host = 'ecard.shanghaitech.edu.cn'` —— 用 **DNS-only 隧道劫持该域名**换取绑定码 |

### 它的技术路径

```
1. 起一个本地 DNS 服务
2. 把 ecard.shanghaitech.edu.cn 的解析劫持到自己的服务器
3. 利用 App 内 WebView 打开绑定页，让绑定码走自己的域名
4. 从自己的服务器上抓到绑定码
5. 用绑定码换 OPENID 会话
6. 用该会话调 eCard API 取付款码
```

### 为什么我们不抄

| 理由 | 说明 |
| --- | --- |
| **小程序做不到** | 微信小程序**没有** DNS / VPN / 网络配置能力。这条路在技术上对我们不存在 |
| **从校园网看是可疑流量** | 劫持学校域名解析，安全部门看到会当成攻击 |
| **脆弱** | 学校改一次 DNS/CDN 就失效 |
| **本质是绕过授权** | 它绕过了「谁能拿绑定码」的设计意图 |

**我们已经把这条写进了 `techpie-integration.md` §6.5 的「不抄清单」。**

## 4. 拿到老师授权之后，正确的三件事

既然你已经在和对应老师申请，**这是最好的时机**。要的东西很具体：

### ① 问一卡通中心要「付款码生成」的接口文档

一句话问法：

> 我们需要在小程序里展示学生本人的校园卡付款码。
> 请问一卡通平台是否提供**付款码生成**接口（不是解码接口）？
> 需要什么资质、什么签约流程？

可能的结果：

| 结果 | 我们怎么做 |
| --- | --- |
| 提供生成接口（token/时间戳/签名） | ✅ 直接实现，最理想 |
| 提供「跳转到一卡通 H5」的 URL | ✅ 用 WebView 打开，最省事，也最安全 |
| 只提供解码接口 | ❌ 对我方无用（那是收银台侧） |
| 需要腾讯微校合作资质 | 走学校统一申请，周期长 |

### ② 问「有没有免登录跳转」

如果一卡通有 **SSO 免登跳转**（带 ticket 直接跳到付款页），那我们只要：

```
用户点「付款码」
  → 我们拿 CAS ticket
  → 跳到 eCard 的 SSO 入口
  → 显示官方付款码
```

**这个方案最优**：我们**不接触付款码本身**，只是把用户送过去。
合规风险最低，实现量最小（一个 WebView + 一个跳转 URL）。

### ③ 明确「不存什么」

申请时主动写明，会显著提高通过率：

- ❌ 不存密码
- ❌ 不存 CASTGC
- ❌ 不存付款码本身（**只做实时转发，不落库**）
- ❌ 不做「代替用户支付」的任何自动操作
- ✅ 只在用户点开时临时获取，用完即弃

## 5. 当前的代码状态（诚实记录）

| 项 | 状态 |
| --- | --- |
| 付款码端点 | `GET /campus-card/payment-code`（契约 `00-FROZEN-CONTRACT.md:1185`） |
| 服务端返回 | **503** —— 真实通道打通前不给假码 |
| 三端客户端 | ⚠️ 都调 `POST`，与契约的 `GET` 不匹配 → 会先得到 404 |
| 契约里的说明 | `campus-services.ts:429` 已登记这个不一致 |

**503 的语义是对的**：宁可明确「暂不可用」，也不返回一个假码让别人以为能付款。
但客户端方法不匹配会让用户先看到 404，看不到那句解释 —— 这是个**已知待修**的小问题。

## 6. 与「统一身份认证」的关系

一个容易混淆的点：**付款码不需要 CAS**。

| 能力 | 依赖什么 |
| --- | --- |
| 余额 / 流水 | eCard 会话（OPENID 或校方 token） |
| **付款码** | eCard 会话 + 校方签发 |
| 门禁 | 校园码（同一套码体系） |
| 课表 / 成绩 | **CAS**（走 eGate / 教务） |

也就是说**校园卡和教务是两条独立的链路**。这解释了为什么 TechPie 把
`campus_card` 的 `FeatureMode` 标成 `native` + `OPENID`，而 `ecourse` 用 `webviewWithCookie`。

对我们的意义：**CAS 没注册下来，不影响付款码；付款码没打通，不影响课表。**

这不是「不做」，是「等真实的接口信息」—— 编一个接口出来只会浪费双方时间。
