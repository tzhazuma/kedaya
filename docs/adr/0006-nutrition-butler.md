# ADR 0006 · 营养管家：数据可信度、识别边界与需求归属

| 项 | 值 |
| --- | --- |
| 状态 | **已接受 (Accepted)** |
| 日期 | 2026-10-17 |
| 决策者 | Lead |
| 影响范围 | `packages/shared/src/nutrition.ts`、`services/api/src/modules/canteen/*`、`apps/miniapp/src/**/nutrition*`、`apps/web/src/**/canteen*`、`docs/architecture/03-api-contract.md` §12 |
| 相关 | [00-FROZEN-CONTRACT.md](../architecture/00-FROZEN-CONTRACT.md) §4 §6.1、[03-api-contract.md](../architecture/03-api-contract.md) §12 |

> **本文档回答一个问题：营养管家的数据从哪里来、能信到什么程度、算错了谁负责。**
> 功能需求本身（用户原话）：*「对于食堂中每一道菜，上传其主要营养成分，然后使用者拍照当餐的菜，或者输入当餐想吃的菜名，营养管家识别菜的种类并计算总营养，推荐当天还需要吃的菜品以满足一天营养需求。当天的营养需求因人而异，具体由使用者提出。」*
> 这句话里每一个分句都对应一个必须显式决策的工程问题，见 §1。

---

## 1. 决策

| # | 决策 | 状态 |
| --- | --- | --- |
| D1 | 营养数据**唯一来源是菜品库**。记录当餐时把菜品库的营养值**快照**进 `MealItem`；菜品日后改营养，**不改写**历史餐记录 | 已决定 |
| D2 | 请求体**不携带营养字段**。客户端只能传 `dishId` / `dishName` / `servings`，营养由服务端解析后落库 | 已决定 |
| D3 | 拍照识别用 **Mock 适配器 + Port seam**。响应带 `mode: 'mock'`，界面**必须**明示「演示期识别」；不编造置信度与营养 | 已决定 |
| D4 | 每日需求**由使用者自行提出**。估算器（Mifflin-St Jeor）只负责**预填**，最终值永远由用户修改后保存 | 已决定 |
| D5 | 六项营养口径：`caloriesKcal / proteinG / fatG / carbG / fiberG / sodiumMg`。**去掉糖**（糖是碳水的子项，GB 28050 口径，避免重复计量） | 已决定 |
| D6 | 缺口 / 汇总 / 估算 / 推荐的计算**全部收敛到 `packages/shared/src/nutrition.ts` 一份纯函数实现**，三端共用；任何端不得另写一套 | 已决定 |
| D7 | 记录当餐**只做精确匹配**（`dishId` 或菜名全等），**不做模糊匹配**。匹配不上明确 400，提示去后台上传 | 已决定 |
| D8 | 「今天」按**本地时区**切天（`shared/time.ts` 的 `dayRange()`），不用 UTC | 已决定 |
| D9 | 推荐必须**可解释**：每条推荐附中文理由（「补蛋白质缺口…；今天还没吃素菜」），禁止输出「算法推荐」 | 已决定 |
| D10 | 本期交付 **小程序全流程（mock 可跑）+ Web 后台菜品管理**；原生端不在本期范围 | 已决定 |
| D11 | 每日需求**一人一份**（`userId` 唯一），`PUT /targets` 语义为 upsert；未设置时 `GET` 返回 `null`，推荐接口 400 引导设置——**不用默认值兜底** | 已决定 |

## 2. 背景

### 2.1 需求逐句拆解

| 用户原话分句 | 对应工程问题 | 本 ADR 的决策 |
| --- | --- | --- |
| 「对于食堂中每一道菜，上传其主要营养成分」 | 营养数据存哪、谁能写、按什么口径 | D1 D5 + Web 后台 `DishManager` |
| 「使用者拍照当餐的菜」 | 识别准确率达不到产品级，演示期怎么办 | D3 |
| 「或者输入当餐想吃的菜名」 | 菜名怎么对到菜品库的记录 | D7 |
| 「识别菜的种类并计算总营养」 | 「种类」= 品类（`DISH_CATEGORIES` 八类），汇总公式 = Σ(每份营养 × 份数) | D6 |
| 「推荐当天还需要吃的菜品」 | 推荐算法放哪、可解释性 | D6 D9 |
| 「当天的营养需求因人而异，具体由使用者提出」 | 需求模型：默认值 vs 用户自填 | D4 D11 |

### 2.2 数据结构上的三个既有事实

| 事实 | 含义 |
| --- | --- |
| 菜品库 `CanteenDish` 由 Web 后台维护，**营养值会被修正**（录入错误、供应商换配方） | 若餐记录只存 `dishId`、读取时 JOIN 最新营养，「上周吃了多少」会被悄悄改写 → D1 |
| 小程序演示期没有真实视觉识别服务，也不该为一个演示功能接付费 API | → D3 |
| 三个端（NestJS / Taro / Next.js）都要展示进度、缺口、推荐 | 三套实现必然漂移 → D6 |

### 2.3 为什么挂在 `canteen` 模块

食堂菜品天然属于 `canteen` 领域。营养管家的端点复用 `modulePath('canteen')` 路由前缀（`/canteen/targets`、`/canteen/meals`…），与菜品 CRUD 同域，不新增模块 ID。这保持了契约 §4 的模块注册表稳定，也让 `canteen` 模块成为 scaffold 生成器中**已挂业务扩展钩子**的先例（SPEC 表驱动，见 `services/api/scripts/scaffold.mjs`）。

## 3. 关键决策的展开

### 3.1 D1：快照防漂移

**问题**：菜品营养会被修正。假设用户周一记录了「红烧肉（当时标 520 kcal）」，周五后台修正为 480 kcal。如果餐记录只存 `dishId`：

- 「本周平均每天摄入」会随菜品库修正而**静默变化**；
- 用户会看到「我没吃东西，热量怎么变了」；
- 医学/营养场景下，历史记录被改写是不可接受的。

**方案**：`MealItem` 落库时拷贝记录那一刻的全部六项营养值（外加 `category`，用于品类均衡统计——品类也可能被改）。`dishId` 保留关联，仅用于跳转菜品详情。

```ts
// services/api/src/modules/canteen/domain/meal.domain.ts（节选）
export interface MealItemModel {
  dishId: string | null;      // 保留关联，不用于读取营养
  dishName: string;
  category: string;
  servings: number;
  // ↓ 记录那一刻的快照，之后菜品库怎么改都不影响这几行
  caloriesKcal: number; proteinG: number; fatG: number;
  carbG: number; fiberG: number; sodiumMg: number;
}
```

**代价（诚实记录）**：冗余存储 + 菜品改营养后，**历史记录不会自动跟随**（这是特性不是 bug，但需要向后台管理员说明：「修正营养只影响之后的记录」）。

### 3.2 D3：识别边界的诚实设计

演示期识别是**确定性 mock**（`mock-dish-recognition.adapter.ts`：对 `imageUrl` 做 djb2 哈希，从候选池确定性选 3-5 个名字）。三条硬规则：

| # | 规则 | 落点 |
| --- | --- | --- |
| 1 | 响应必须带 `mode: 'mock'`，前端原样透展示示 | `POST /canteen/recognize` 响应体 |
| 2 | 候选**不编造营养**：识别到的名字去菜品库精确匹配，匹配不上 `dish: null`，UI 提示「识别到但菜品库还没有，请手动选择」 | `MealService.recognize()` |
| 3 | 置信度只是 mock 的展示值，**不参与**任何落库决策 | 仅 UI 展示 |

Port 定义在 `domain/recognition.domain.ts`（`DishRecognitionPort`，token `DISH_RECOGNITION`），未来接真实视觉服务只需新增一个 adapter 并在 `canteen.module.ts` 换绑定，**use case 零改动**。

### 3.3 D4 + D11：需求归属与「不兜底」

用户原话「当天的营养需求因人而异，具体由使用者提出」被严格实现为：

- `GET /canteen/targets` 未设置 → 返回 `null`（**不是**一个默认需求）；
- `GET /canteen/recommendations` 未设置 → `400 VALIDATION_FAILED`，message 直接引导 `PUT /canteen/targets`；
- 估算器 `POST /canteen/targets/estimate` 是**纯计算不落库**，前端拿它预填表单，用户逐项修改后自己保存。

**为什么不给默认值**：营养需求是健康相关数据，一个「猜出来的默认需求」会让缺口与推荐失去意义，且用户根本不会发现它在用一个错误的目标。**明确失败优于静默兜底。**

### 3.4 D5：六项口径与去糖

| 字段 | 单位 | 语义 |
| --- | --- | --- |
| `caloriesKcal` | kcal | 目标值 |
| `proteinG` | g | 目标值 |
| `fatG` | g | 目标值 |
| `carbG` | g | 目标值 |
| `fiberG` | g | 目标值 |
| `sodiumMg` | mg | **上限值**（超过即超标） |

**去糖（2026-10-17 决策）**：原设计七项含 `sugarG`。用户指出「糖包含在碳水里了吧」——正确，GB 28050 中糖是碳水化合物的子项。保留两项会导致：① 同一能量来源在 UI 上出现两次，用户误以为要分别凑两个目标；② 菜品录入多一个可漏填字段。已全仓库摘除（`NUTRIENT_KEYS` / schema / SPEC / 三端），`git grep sugarG` 为零。

### 3.5 D6：单一计算核心

`packages/shared/src/nutrition.ts` 是纯函数文件（无框架、无 IO），导出：

| 函数 | 用途 |
| --- | --- |
| `sumItems` | 一餐/一天汇总：Σ(每份营养 × 份数) |
| `computeGaps` | 缺口 = 目标 − 已摄入（钠为上限 − 已摄入，负数=超标） |
| `estimateDailyTargets` | Mifflin-St Jeor 估算（见 §3.6） |
| `recommendDishes` | 缺口加权打分 + 热量预算惩罚 + 钠上限惩罚 + 品类均衡加成 |
| `validateDishInput` | 菜品录入校验（小程序表单与 Web 后台共用同一份规则） |

后端 service 只做编排（取数 → 调 shared → 组装），小程序 store 与 Web 的派生展示同样调用它。**测试策略因此简单**：shared 单测覆盖全部计算，service 单测只测编排。

### 3.6 估算器公式与依据

Mifflin-St Jeor（目前临床与健身界最常用的静息代谢率公式，1990 年发表，较 Harris-Benedict 在现代人群中误差更小）：

```
BMR(男) = 10 × weightKg + 6.25 × heightCm − 5 × age + 5
BMR(女) = 10 × weightKg + 6.25 × heightCm − 5 × age − 161
TDEE    = BMR × 活动系数
```

| 活动等级 | 系数 |
| --- | --- |
| sedentary（久坐） | 1.2 |
| light（每周 1-3 次） | 1.375 |
| moderate（每周 3-5 次） | 1.55 |
| high（每周 6-7 次） | 1.725 |

目标调整与供能比：

| 目标 | 热量系数 | 蛋白 | 脂肪 | 碳水 |
| --- | --- | --- | --- | --- |
| 减脂 lose | ×0.85 | 25% | 30% | 45% |
| 维持 maintain | ×1.0 | 15% | 25% | 60% |
| 增肌 gain | ×1.15 | 20% | 25% | 55% |

**安全底线（硬编码）**：热量不低于 `CALORIE_FLOOR_KCAL = 1200` kcal（避免激进出货低于基础代谢），蛋白质不低于 1 g/kg 体重。膳食纤维按每 1000 kcal 14 g（中国居民膳食指南推荐量），钠上限固定 2000 mg（约 5 g 食盐，膳食指南上限）。

**诚实标注**：供能比区间参照通行膳食建议取值，**不是**针对个体的医学处方；公式误差在个体上可能达 ±10%。这就是 D4「只预填、用户自提」存在的原因——估算器降低填写门槛，但不冒充医学建议。界面应附一句「估算值仅供参考，请按自身情况调整」。

### 3.7 D7：为什么不做模糊匹配

「宫保鸡丁」vs「宫保鸡丁（微辣）」vs「宫保鸡丁饭」——模糊匹配在菜名场景下**极易记错**：匹配错一道菜，整餐营养全错，且用户很难察觉。宁可让记录失败并提示，不许静默记错。后台上传缺失菜品是显式引导路径（小程序「菜品库没有？」入口 + Web 后台 `DishManager`）。

## 4. 被否决的方案及理由

### 方案 A：信任客户端提交的营养值（请求体带六项）

**描述**：`POST /meals` 的 items 直接带营养数值，服务端只存不算。

| # | 否决理由 |
| --- | --- |
| 1 | 客户端可提交任意值，「吃了 100 kcal 的炸鸡」这种数据毫无意义 |
| 2 | 小程序与 Web 各有一份「每份营养」数据源，必然与菜品库漂移 |
| 3 | 违背需求原话「上传其主要营养成分」的定位——营养是菜品库的属性，不是每餐的属性 |

### 方案 B：餐记录只存 `dishId`，读取时 JOIN 菜品库最新值

**描述**：不冗余存储，永远显示「当前口径」的营养。

| # | 否决理由 |
| --- | --- |
| 1 | 菜品营养修正会**静默改写历史**（§3.1）——用户没吃东西热量却变了 |
| 2 | 菜品被删除后历史记录读不出营养（除非软删除+永久保留，复杂度转移到另一处） |
| 3 | 「记录那一刻的真相」在营养场景比「永远最新」更有价值 |

### 方案 C：演示期接真实视觉识别 API（如通用物体识别）

**描述**：接一个真实的图像识别服务，至少识别结果是「真」的。

| # | 否决理由 |
| --- | --- |
| 1 | 通用识别（「这是米饭」）与菜品库（「第二食堂一楼的红烧肉」）粒度不匹配，识别结果大概率匹配不上菜品库，用户体验更差 |
| 2 | 引入付费 API 密钥、网络依赖、失败态处理，为一个演示功能显著增加系统面积 |
| 3 | 识别不准时的错误提示更难做（mock 的诚实「演示期」标注反而更清晰） |
| 4 | **保留**：Port 已留好（D3），接真实服务是 adapter 级替换，不是重构 |

### 方案 D：给一个默认每日需求（如 2000 kcal 通用值）

**描述**：用户不设置也能用，推荐系统拿通用默认值跑。

| # | 否决理由 |
| --- | --- |
| 1 | 违背用户原话「具体由使用者提出」 |
| 2 | 静默使用错误目标 = 推荐与缺口失去意义，且用户无从察觉 |
| 3 | 通用值对 50kg 与 100kg 的用户都是错的 |

### 方案 E：保留七项（含 `sugarG`）

**描述**：GB 28050 有糖字段，就按国标全收。

| # | 否决理由 |
| --- | --- |
| 1 | 糖是碳水化合物的**子项**（同属碳水化合物大类），两项并列让用户误以为要分别凑目标 |
| 2 | 菜品录入多一个可漏填/错填字段，Web 后台与小程序表单都要为它加校验 |
| 3 | 缺口与推荐的计算口径不变（糖不参与打分），保留它只有展示成本没有决策价值 |

### 方案 F：每端各写一套缺口/推荐计算

**描述**：后端算推荐的，小程序本地再算一份进度（省请求）。

| # | 否决理由 |
| --- | --- |
| 1 | 三套实现必然漂移——小程序显示「还差 62g 蛋白」而后端推荐按 58g 算，用户看到矛盾 |
| 2 | 修正算法要改三个地方、跑三套测试 |
| 3 | 纯函数放 shared 后本地计算与请求的计算**本来就是同一份代码**，没有为「省请求」牺牲一致性的理由 |

### 方案 G：记录当餐用菜名模糊匹配

**描述**：用户输入「西红柿鸡蛋」，能匹配到「番茄炒蛋」之类的近似菜。

| # | 否决理由 |
| --- | --- |
| 1 | 菜名近似 ≠ 同一道菜（分量、做法、配料全不同），匹配错则整餐营养错误且难察觉 |
| 2 | 模糊语义需要同义词词典，维护成本无底洞 |
| 3 | 明确失败 + 引导上传的路径更诚实（§3.7） |

### 方案 H：按 UTC 切天

**描述**：`today` / `meals` 用 UTC 日期划分。

| # | 否决理由 |
| --- | --- |
| 1 | 用户在北京时间 23:30 吃的夜宵，按 UTC 算进「明天」——「今天吃了多少」直接答错 |
| 2 | 已有时区助手 `shared/time.ts` 的 `dayRange()`，本地切天不增加实现成本 |

## 5. 后果

### 5.1 正面后果

| # | 后果 |
| --- | --- |
| 1 | 营养数据可信度有单一来源（菜品库），历史记录不被静默改写 |
| 2 | 识别能力的演示边界诚实可见（`mode: 'mock'` + `dish: null` 提示），不制造「AI 很准」的错觉 |
| 3 | 三端计算零漂移，测试只需覆盖一份纯函数 |
| 4 | 需求归属清晰（用户自提），推荐接口不兜底，错误状态可引导 |
| 5 | 推荐理由可解释，用户能看懂「为什么推这道菜」 |
| 6 | 视觉识别可平滑升级（Port + adapter），use case 不动 |

### 5.2 负面后果（必须承认）

| # | 负面后果 | 严重性 | 缓解 |
| --- | --- | --- | --- |
| 1 | 快照冗余存储，菜品改营养后**历史不跟随** | 中 | Web 后台菜品表单加提示「修正只影响之后的记录」；ADR 明示这是特性 |
| 2 | 演示期识别准确率低，用户可能记不上想吃的菜 | 中 | 手动输入菜名路径始终可用；「菜品库没有」引导上传 |
| 3 | 精确匹配导致记录失败率高（菜名差一个字就不行） | 中 | 小程序菜品选择器带搜索；Web 后台批量录入 |
| 4 | 估算器公式有个体误差（±10% 量级），可能被当成医学建议 | 中 | 界面标注「仅供参考」；D4 用户自提兜底 |
| 5 | 推荐算法是手工加权，不是学习模型，长期天花板明显 | 中 | D9 可解释性优先；未来可替换 `recommendDishes` 实现（shared 内单点替换） |
| 6 | 钠上限惩罚与品类加成是拍脑袋权重（0.2 / 0.05） | 低 | 已集中在 shared 一处，调参只改一处 |
| 7 | 本期 mock 数据不进真实数据库，联调前推荐质量未经真实数据验证 | 中 | 任务清单含 typecheck/单测；真实联调排在后续 |

## 8. 修订记录（2026-10-17 · 代码评审后）

第一版实现跑通了「记录 → 汇总 → 缺口 → 推荐」，但评审发现**闭环与可信度**有硬缺口。
本节记录新增决策，编号接 §1 的 D1–D11。

| # | 新增决策 | 解决的问题 |
| --- | --- | --- |
| D12 | **当餐可删可改**：`DELETE /canteen/meals/:id`、`PATCH /canteen/meals/:id`（餐型 / 备注 / 份数） | 原实现只能新增，记错一顿就永久污染当天进度。改菜不支持：换菜 = 换营养快照，等同重记 |
| D13 | **份数 0.5 步进**（0.5–20），`MealItem.servings` 改为 `Float` | 食堂的「半份」是常态，整数份数会让人少记或放弃记录；`sumItems` 不再 `Math.trunc` |
| D14 | **幂等键**：`Idempotency-Key` 头 / `clientRequestId` 字段，`@@unique([userId, clientRequestId])` | 弱网重试与双击会把一餐记成两餐，而重复计热量是**静默错误** |
| D15 | **身体档案随需求保存**（sex / age / heightCm / weightKg / activity / goal，均可空） | 原实现每次重估都要重填一遍；体重变了也无法一键更新目标，「因人而异」变成一次性动作 |
| D16 | **时区显式化**：服务端按 `APP_TZ_OFFSET_MINUTES`（默认 480）切天 | 原实现依赖进程 TZ：开发机对、UTC 容器错 8 小时，早餐被算进昨天 |
| D17 | **菜品库写操作要管理员**（`AdminGuard`，fail-closed）+ **软删除**（`deletedAt`） | 原实现任何匿名请求都能改营养值或删空菜品库，而 D1/D7 全都建立在「菜品库是权威数据」上 |
| D18 | **推荐排除今天已吃**（按 `dishId` 硬过滤）+ 候选池改为「未下架、最近维护优先」 | 原实现会推荐刚吃完的那道菜；候选池按 id 升序取前 100，新录入的菜永远进不了推荐 |
| D19 | **录入校验双层**：`validateDishInput`（服务端也跑一遍）+ `checkDishEnergyConsistency`（4×蛋白+4×碳水+9×脂肪 对热量） | 营养值全是人工录入，少打一位数会让缺口与推荐全盘错，而用户察觉不到 |
| D20 | **历史视图与趋势**：`GET /canteen/stats?days=`、`GET /canteen/dashboard` | 只能看「今天」等于趋势数据白存；`dashboard` 把首页的三次往返压成一次 |
| D21 | **隐私分级上调**：`canteen` 从 `low` 改为 `medium`（仍不设同意门，但写操作落审计） | 每餐记录 + 身体档案可推断健康状况，与「菜品营养表」不是一个敏感度 |
| D22 | **过敏原/忌口硬过滤**：`CanteenDish.allergens` + `NutritionTarget.avoidAllergens`，`recommendDishes({ excludeAllergens })` 命中即**整道排除**（不打分），记录前弹一次确认 | 过敏是安全问题：扣分意味着「还是会出现」，不可接受。菜名关键词推断 + 后台可修正，界面必须明示「可能标注不全」 |
| D23 | **餐型维度汇总**：shared 的 `sumByMealType()` 把当天压成「早/午/晚/加餐」四行（四类恒定返回），首页展示各餐热量占比 + 「蛋白最不够的一餐」提示 | 整天汇总说不出「下一顿该补什么」；按餐型看才能给出可执行建议 |
| D24 | **季度饮食形象**：shared 的 `computeDietPersonas(days, target, 90, coverage)` 用**可读规则 + 阈值表**（`PERSONA_RULES`）把 90 天记录归纳成**一组**人设标签（新人驾到 / 奶茶妹 / 蛋白猎人 / 素食主义者 / 肉食主义者 / 重口战士 / 早餐逃兵 / 自律达人 / 食堂探索家），按强度排序，主形象取最强的一个，必须同时展示 `evidence` 判定依据 | 分享性最强的一屏，但不能是黑盒打分：每个标签都要能说出「凭这 3 条数据」。**一个人可以同时有多个形象**（既喝奶茶又自律），只给一个会丢信息；数据不足时明确说「还看不出」，不硬凑 |
| D24.1 | 「食堂探索家」的判定条件是**菜品覆盖率 > 80%**（窗口内吃过的不同菜品 / 未下架菜品总数），覆盖率由 `GET /canteen/stats` 的 `coverage` 字段提供 | 「吃得杂」这件事只能靠覆盖率说清楚；用「品类数」会被 8 个品类上限卡死 |
| D25 | 为支撑形象判定，`GET /canteen/stats` 的 `days[]` 增加 `mealCounts` / `itemsByCategory`（当天现算，不落库），`days` 上限从 60 放宽到 **92** | 饮品/甜品占比、早餐记录率这些维度，只有按天保留餐型与品类条数才算得出来；季度 = 90 天

**仍然未做（明确记录）**：真实视觉识别（D3 的 Port 仍在）、下架菜品的静默期提醒、
`snack` 是否计入当日汇总（原 C6）、多套目标模板、**新录入菜品的过敏原自动推断**
（D22 的过敏原过滤已上线，但只有种子脚本按菜名推断；Web 后台新建的菜品 `allergens` 为空，
过滤对它们不生效 —— 见 C8）。
